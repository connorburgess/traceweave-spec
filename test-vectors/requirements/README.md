# Complete MUST inventory — M5.1

[requirement-map.json](requirement-map.json) extends the reviewed [M1.5 extraction map](../extraction/requirement-map.json); it does not replace it. [tools/check_requirement_map.py](../../tools/check_requirement_map.py) scans every UTF-8 file recursively in `spec/` and `profiles/`, including newly added files, and accounts for every uppercase whole-word `MUST` occurrence (including `MUST NOT`, definitions and external quotations). Lowercase ordinary-language “must” and requirements expressed solely with other keywords are outside this gate's inventory.

There are **157 mapped occurrences**, **0 unmapped**: 100 testable, 13 implementation-test, 27 requiring non-executable inspection, 17 definitional/quoted. These numbers include the original extraction map's 28 occurrences. The map stores exact source passages, one clause per occurrence, stable entry IDs and reasons. Line numbers in `section` are convenience locators; verbatim passage matching is authoritative. A changed passage, unknown evidence ID, missing negative, missing spot-check designation, duplicate entry or unmapped occurrence fails validation.

## Evidence forms and failure meaning

- Existing M1.5 IDs retain their original interpretation (`cfg`, extraction vector IDs, `record`, `selftest`, `checker`, `impl`). `impl` references are checked only with `TW_IMPL_REPO` set; an unset checkout is reported as unverified, never as a passing implementation rerun.
- `vector:<repository-path>:<id>` names a promoted extraction vector. Negative references require its `result.status` to be `error`. Promoted checkers require exact expected results, so accepting such an input fails byte/result comparison.
- `rejection:<repository-path>:<id>` names a paired text-output corruption in `rejections.json`, with an explicit mutation and expected failing layer. The text checker independently applies and rejects it.
- `negative:<repository-path>` names a registration rejection fixture with an explicit `fixture.expect.code`. The registration checker requires that rejection, not merely a generic failure.
- `unittest:<path>:<Class.test_method>` resolves an actual AST-declared test method containing assertions. [release requirement tests](../../tests/test_release_requirements.py) execute radix cases and seven mutants, 35 invalid-policy variants plus five strict-JSON negatives with an evidence-access trap, size/stream boundaries, wrapper identity, rendering, selection and placeholder cases. Rendering and selection use explicit test-only output adapters; they are not implementation/Shelf certification.
- `registered:<id>` names an explicit entry in [checker-tests.json](checker-tests.json), pinning a checker self-test locator and failure description. Arbitrary source text such as `import json` cannot replace a release-map test ID.
- The delegated extraction map’s `checker:<path>:<text>` retains the M1.5 convention: the named test/mutation locator must occur in the checker source. A human reviews whether it tests the mapped violation; source-string existence is not proof of logical relevance. The referenced checkers run through `tools/validate.py`, including the nine [release boundary probes](../../tools/check_release_boundaries.py). `failsBecause` states what rejects the violating output. Positive acceptance requirements use a deliberately corrupted expected result or wrong implementation as their negative fixture, rather than incorrectly calling a valid input an error.

## Non-author spot-check worksheet

All 27 remaining inspection clauses and the definitional/quotation clauses are marked `spotCheck`. “Untestable” is reserved for asymptotic/internal properties, historical byte retention, production deployment choices, future registration review and open-ended human semantic judgement. Executable process, resource, selection and display rules are not waived merely because they are outside output bytes: they now have fixture/adaptor or pinned implementation tests. It does not mean the obligation is waived. Reasons state the inspection boundary, rather than presenting a loosely related fixture as conformance evidence.
