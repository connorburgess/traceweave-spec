# WEB.6 prospective budget amendment — PROPOSED

2026-11-27. **Draft for owner decision and independent review; not adopted, frozen, implemented or tested.** Draft base: curated publication-source `329c0b8d8642ff3c07d258f9a7944c70f9dd1d14`. This draft changes no gate, count, criterion, runtime hold or implementation. WEB.3–WEB.6 remain planned; core remains 34/47 met, later gates 28/55 met plus two negative results. M3 execution/acquisition, hosted services and publication holds remain in force. Public-document reading and static local source inspection are the only research performed here.

## 1. Temporal prerequisite and proposed amendment

The [existing WEB.6 row](../../ROADMAP.md) requires further budgets to be frozen before WEB.1 starts. WEB.1 is already recorded met at implementation `51f29d7`. The owner-supplied research and [retained dependency audit](../reviews/web5-existing-claims-20261126/README.md) report no sufficient earlier freeze record located. The bounded record inspected here does not establish compliance with that temporal prerequisite. This proposal acknowledges it as missed on the available evidence; it does **not prove the absence of every possible earlier record**, invalidate engine results, or invent a retrospective freeze. A newly discovered earlier record would require separate provenance/scope review, not automatic historical compliance.

Propose replacing **only** this current WEB.6 sentence:

> Further budgets are frozen before WEB.1 starts.

with these exact sentences, subject to owner approval and independent review:

> The pre-WEB.1 budget-freeze prerequisite is acknowledged as missed on the available recorded evidence; this does not prove that no earlier record exists or establish retrospective compliance. Further budgets are instead frozen prospectively in a versioned, independently reviewed acceptance protocol before the WEB.6 conformance run; that protocol records the supported flows, byte and entry limits, device/browser versions, numerical thresholds, test counts, measurement limits and all baseline-dependent decisions. WEB.6 remains planned until its unchanged keyboard and input-boundary requirements and the prospectively frozen budgets pass with filed evidence and non-author review.

The other three criterion sentences remain **verbatim**:

> Accessibility and performance budgets are decided by counts. Each flow can be completed keyboard-only (k/k flows). A stated maximum input size applies, with a clear refusal above it, tested at the limit and one byte over.

This is a proposed text replacement, not an edit to ROADMAP. Adoption of an amendment would permit a later protocol freeze, not retroactively satisfy the original timing clause or itself close WEB.6. Existing WEB.0 start authorization is not requested again.

## 2. Scope and current constraints

The [source-validation ledger](web6-budget-source-validation.md) separates standards, guidance, engineering proposals and actual code observations. The recorded 1,128,365-byte WASM artifact is **uncompressed historical engine evidence** from `51f29d7`, not a current UI build, transfer budget, compilation measurement or browser support certificate. No new artifact was built or measured.

Static inspection of implementation `dcaa0d42e9de63d23aa113d9306134de9b28942c` finds a maximum configurable extraction input of **8,388,608 bytes (8 MiB)**. Shelf `86036c43394e94c1431ca335195a86e7754da6df` selects **1,048,576 bytes (1 MiB)** in its comparison extraction config. Neither is a verified browser-memory envelope. The wrapper reads a whole WASM response, copies complete input buffers into WASM memory and returns copied output; its exported processing calls are synchronous. Shelf comparison uses complete strings/catalogues; registration file pickers read whole buffers/text. These observations do not prove UI refusal before reading, bounded peak memory, cancellation, streaming or main-thread responsiveness. Effect-suppression flags are not computation cancellation. A worker-based design is a **practical proposed implementation constraint**, not a WASM/WCAG specification fact or existing parity result.

## 3. Candidate limits and units

All values below are **proposed engineering targets for review**, not support promises. B means exact bytes; KiB = 1,024 B; MiB = 1,048,576 B. Network rates use decimal bits/s; ms and s are elapsed durations. Input text is counted as UTF-8 bytes, including encoded line endings, not JavaScript UTF-16 length or character count. No silent normalization, truncation or config increase is allowed. Limits are part of the displayed UI contract, distinct from smaller protocol/config limits.

| Limit | Candidate value | Proposed enforcement and boundary tests |
| --- | ---: | --- |
| Each source file or pasted source for F/C | `min(1,048,576 B, config.maxInputBytes)` | Preserve the selected config; preflight File.size or bounded UTF-8 encoding. Valid in-limit fixture at L, same fixture plus exactly one byte at L+1; assert clear refusal above L before engine processing |
| Source count and aggregate sources per job | 32 files; 8,388,608 B total | Check 32/33 and aggregate L/L+1, including individually valid files; sums checked without overflow |
| Each catalogue or replay-report document | 4,194,304 B | Both sides independently checked at L/L+1; bound raw read before parsing. Invalid/malformed documents tested separately from size rejection |
| Catalogue entry count | 1,000 entries per catalogue | Parse only after byte bound; test 1,000/1,001 valid entries; do not call this an engine limit |
| Combined input payload per core job | 8,388,608 B including report/catalogues/config/auxiliary bytes | One explicit byte ledger; count original bytes even when UI-to-worker framing expands them; also applies when individual limits pass; at L/L+1 tests |
| Exported catalogue/report | 8,388,608 B | Abort with explicit output-limit result; no downloadable partial or silently shortened output. Generation memory must remain bounded independently |
| Work concurrency | One active job per tab; at most one source loaded into engine at a time where catalogue API permits | Queue/reject second job clearly, never permit hidden multiplication of memory. Whole-job framing in the present API is a known design gap |

The source cap cannot be widened to 250 MB under this draft: the report supplies no browser capacity measurement, and 250 MB exceeds the engine's existing extraction config bound. The suggested 50 MB/20,000-entry catalogue and 500 MB memory promises likewise lack Traceweave evidence. They are not adopted. Even the smaller candidate limits above require baseline feasibility and independent boundary checks. For at-limit fixtures, distinguish successful size admission from any independently valid protocol refusal: record CLI-equivalent outcome, and include a well-formed fixture that actually completes each supported subpath. A timeout, crash or “too large” refusal at a promised in-limit case is not a pass.

No total processing duration is derived from Core Web Vitals. Progress and cancellation expose actual design gaps: a worker stuck inside synchronous WASM cannot post genuine incremental progress or consume a cancel message until it returns. For disposable core F/C/V work, the proposed solution is honest indeterminate UI plus host-controlled termination; adding instrumented phases/chunking is future implementation, not a claim about current exports. UI timers cannot stand in for measured progress or prove that the worker is alive.

Memory API evidence is conditional. `measureUserAgentSpecificMemory()` is limited/experimental, requires a secure cross-origin-isolated context and returns implementation-dependent values. COOP `same-origin` and COEP `require-corp`/`credentialless`, permissions and resource compatibility require separate analysis; this draft does not authorize header changes that could break embedded resources/popups. Missing API support is “not measured,” never zero or pass. Prefer portable bounded-input/allocation evidence plus browser-specific traces; explicitly mark what remains unobservable before freezing P9 [L12–L13].

Measurement availability is a required per-cell record [L18]. Before future collection, feature-detect the observer itself and each needed `supportedEntryTypes` value in the relevant window/worker context; successful construction alone does not establish LCP, event timing or long-task coverage. Record unavailable entry types, empty/missed buffers, timer precision, trace tooling and instrumentation overhead. Empty observations are not evidence of zero long tasks or zero latency.

Fallbacks must retain the measured quantity: browser performance traces with input and presentation timestamps may substitute for event timing only when their precision and phase coverage support the same limit. A callback timestamp, UI heartbeat or `requestAnimationFrame` alone does not establish that feedback painted. If LCP cannot be observed, report LCP unmeasured; the separately defined shell-ready mark is useful diagnostics, not replacement LCP or INP. Where long-task observers are absent, an independently reviewed browser trace may provide equivalent main-thread duration/attribution evidence; a timer-lag check alone cannot prove the zero-long-task count. For memory, retain bounded-allocation and linear-memory evidence as separately scoped observations; neither a process sample nor a buffer ledger silently substitutes for an unavailable whole-context peak measurement.

A required metric/device cell without an adequate observer or reviewed equivalent is **unmeasured, not passed**. Report the denominator as planned/measured/passed, retaining unavailable cells. Before a conformance run, the protocol must resolve instrumentation or obtain an explicit reviewed change to the proposed metric/support envelope; it cannot claim the original threshold passed or silently drop the device after collection. This fallback policy authorizes no instrumentation deployment, header change or runtime test now.

## 4a. Core cancellation allocation and active-probe validity (R2)

The minimum P7 allocation is **ten valid active probes per phase**, not ten distributed across phases. Four core subpaths are F, C catalogue–catalogue, C catalogue–files and V; two required physical cells are D1 and D2. Exactly three proposed processing phases apply to each: **early** (bounded input read/decode after work starts), **mid** (bulk extraction/compare/replay engine work), and **late** (real result-copy/serialization/finalization work before publishing the result). These are work phases, not percentages of elapsed time or timers pretending to know progress. A completed kernel can still precede actual finalization work, but a completed job merely awaiting a click/download is not active finalization.

| Allocation, one exposed profile/config tuple per subpath | Planned active probes |
| --- | ---: |
| Each `(subpath, profile tuple, physical cell, phase)` | 10 |
| Each `(subpath, profile tuple, physical cell)`, three phases | 3 × 10 = 30 |
| Each physical cell, four subpaths | 4 × 3 × 10 = 120 |
| Both required physical cells | **2 × 4 × 3 × 10 = 240** |

Ten is a proposed practical repeat count to expose repeatability and boundary races on each device; it is not a statistical reliability bound. If `p_s` is the number of exposed profile/config tuples for subpath `s`, the required total is **10 × 3 × 2 × Σ p_s = 60 × Σ p_s**, summed across all four subpaths. Four subpaths with one tuple each give 240; a uniform `p` tuples gives `240 × p`. Mixed-profile/config scenarios exposed by the UI must be enumerated as tuples, not silently pooled. D3 diagnostics have a separate `10 × 3 × Σ p_s` count (minimum 120), never a substitute for D1/D2. D and R are excluded from this core denominator and retain distinct protocols.

Before freeze, the manifest must bind each subpath/tuple to concrete workload, phase-entry/exit evidence and cancel trigger. The current API is not claimed to expose those boundaries. A baseline must show all three real phases are observable and long enough to obtain active probes within the proposed caps. An artificial wait/barrier with no processing underway cannot be the only evidence of an active phase. If a proposed phase does not exist or cannot be measured, retain its planned bucket as unavailable; either resolve feasibility or obtain a reviewed protocol/proposal change **before** a conformance run. No post-run subtraction or relabelling is allowed; any approved extra phases expand the formula explicitly.

For a valid active probe, recorded evidence must show: job admitted and processing begun; the cancel event was received before phase exit/job completion/result publication; the named phase was actually active at that event; and observer coverage supports acknowledgement, cessation/result invalidation and restart timings. Freeze a common timeline or calibrated cross-context clock relationship; unsupported timing is unmeasured. A request arriving after completion is logged as an invalid/inactive attempt, not one of the ten active successes. Record every attempt and reason; an invalid attempt leaves its planned slot unmeasured until a replacement allowed by the predeclared validity rule is collected. Preserve every valid failure; do not rerun valid misses until ten successes hide them. Report planned/valid-measured/passed, invalid attempts and unavailable slots **per bucket**, with 10/10 required in every physical-cell bucket, not just a pooled 240/240. Reuse a P4 Cancel observation only if it also satisfies these phase/validity conditions and is explicitly cross-referenced; do not add its count twice.

## 4b. R cancellation and committed effects (R1)

**R is not disposable core computation.** P7's 1,000 ms termination/result-discard promise does not govern registration key persistence, signing or card storage. A registration cancellation requests **stop scheduling future steps**; it does not reverse a key write, completed signature or saved card. Pure supplied-input R verification may use a disposable worker, but terminating that worker cannot discard an earlier signing/storage receipt or change the truth of those effects. This distinction changes no key/default policy, consent, storage permission or cryptographic claim, and does not authorize an R implementation now.

Pinned Shelf source sequences `onEnsureKey` → signing → supplied-input verification → `onCardCreated`; key creation can persist a new key, signing awaits Web Crypto, and the card callback saves to localStorage (ledger local boundary row). The following is the **proposed** cancellation state contract, not a description of implemented cancellation controls. A future implementation needs explicit guards and effect accounting at these boundaries; current effect-suppression flags do not supply them.

| State when cancellation is accepted | Proposed stop boundary and truthful outcome |
| --- | --- |
| R0 — before key acquisition/generation begins | Do not enter key generation/persistence, signing or card creation. Report stopped before effects only if the operation record proves none began. Reusing an existing key is separately identified, never reported as a new key |
| RK — key generation/write started, before signing | Stop before any not-yet-entered persistence/signing step. If a key write has already entered its commit boundary, let its outcome settle and record persisted/failed/unknown. A generated but not persisted key does not imply a saved key. If persistence completed, report **stopped; key saved; not signed; card not saved**. Do not delete that key or create another as cleanup/recovery |
| RS0 — key outcome known, before signing invocation | A guard before the signing call prevents it when cancellation is already accepted. Report existing/newly saved key status and not signed/not saved. A key saved by this job remains saved; cancellation is not rollback |
| RS1 — signing invoked/in flight | The inspected path has no application abort mechanism for its signing promise. Acknowledge stop requested; do not claim signature cessation within 1,000 ms or discard its eventual outcome. Stop subsequent verification/card-save steps not yet entered; when signing settles, report signed/not signed/error/unknown truthfully and retain the result receipt. A completed signature is not undone by terminating another worker |
| RB — signature completed, before card-store commit (including verification in progress) | Preserve the signed-result receipt; stop later work and skip a not-yet-entered card callback/save. Disposable verification can terminate separately. Report **signed; card not saved; verification completed/not completed/error**, with key status. Do not say cancelled with no effects or silently lose the signed bundle as a late core result |
| RC — card callback/store commit entered or already returned | Do not promise interruption of a synchronous store/callback already entered. Settle and reconcile actual storage status. Confirmed write: **completed/saved; stop arrived too late for this effect**, even if further presentation work stops. Failure: report write error plus known effects. Ambiguous/partially observed callback: report storage outcome unknown and recovery status, not “not saved.” Discarding a UI/worker response cannot undo the write |

A future host defines the ordering of cancellation acceptance and each commit-entry guard in the operation log. A queued click received only after a synchronous write completed is a post-commit request; do not retroactively timestamp it as having prevented the write. UI state updated before storage acknowledgement is not proof of persistence. Synchronous calls and Web Crypto promises are not made transactionally atomic by this proposal.

**Receipt/status recovery.** Maintain a session-local operation ID and read-only status receipt: request/artifact digest; selected key identifier/fingerprint and reused/new status; key-write started/confirmed/failed/unknown; sign started/completed/error/unknown and signed-bundle digest; verification result or not completed; card ID, store attempted/acknowledged/reconciled/failed/unknown; cancellation accepted time/boundary and terminal/partial/pending status. No private-key bytes, new raw-content copy, network transmission or new persistent receipt journal is authorized. Retain an already-created signed bundle in the existing operation's transient recovery context rather than silently discarding it; viewing/exporting/saving it remains subject to existing policy/consent and an explicit user action, not an automatic follow-on after cancellation.

Recovery reads existing state using recorded key/card IDs and matching digests, displays known effects and identifies uncertainty. A matching localStorage read-back can confirm session-visible content, not durable disk flush or crash safety; absent/changed/concurrently modified storage or missing observations must not be guessed. A reload may lose the transient receipt; disclose that limitation and use only already-authorized existing key/card records, otherwise report unresolved outcome. Do not add a background journal, delete a persisted key/card, roll back trust/policy, generate another key, retry signing, re-enter a save callback or submit externally as recovery. A later deliberate new action uses existing consent controls and a new operation ID; a recovery check itself cannot perform it. Errors/timeouts preserve the same partial-effect accounting. This is status recovery, not an idempotence or exactly-once transaction claim.

**R-specific proposed acceptance.** Foreground stop-request acknowledgement still targets ≤200 ms; within 1,000 ms expose either a reconciled result or truthful **stop requested / commit pending**, with known effects, rather than a false “cancelled” terminal state. No promise is made that an in-flight sign/store stops within that second. Proposed settlement target is ≤30,000 ms desktop/≤60,000 ms mobile from the accepted stop request, baseline-dependent and separately reported from P7. Exceeding it fails that R target and remains pending/unknown; it cannot be labelled successful cancellation. A late completion updates the original receipt without resuming skipped steps or starting a retry. Completion of a committed effect after a stop request is an observed outcome to report, not evidence that rollback worked.

If R ships, a separately reviewed manifest must enumerate pre-key, key-write, pre-sign, in-flight-sign, post-sign/pre-store/verification and post-store cancellation cases; reused/new key branches; storage/sign errors and ambiguous outcomes; late messages, duplicate actions and reload receipt loss. Freeze per-case/device counts before any R run and report planned/measured/passed separately from core 240+ and R's 2/2 keyboard tasks. Assert observed existing key/card records and receipt truth for each case; a worker-disappeared/UI-idle assertion alone cannot pass it. UI must explain before committing that cancellation stops future steps and cannot undo saved effects; an unavoidable boundary must stay visibly pending until its outcome is known. None of these tests is performed or authorized here. R cannot be marked cancellation-ready by passing P7 alone.

## 6. Reproducible prospective protocol and open decisions

Before a conformance run, independent review must accept a manifest with exact source/deployed-asset identity, fixtures/configs/CLI expected bytes, all limit dimensions, required cells, repeated-run order, measurement tools/versions and thresholds. A clean cold run clears HTTP cache and disables any existing service worker; warm means the same pinned assets loaded once, no source/user data persistence inferred. P2 means five cold navigations and five warm navigations per required physical cell to the same route/version; P3 means five first-use engine-preparation runs per required cell, recorded separately. Five cold/warm trials are small lab samples with all samples/max reported; do not relabel them as field p75. Keep profiled and unprofiled timings separate because instrumentation adds overhead. Predeclare invalid-run conditions (OS update/interruption/tool failure); preserve failed traces and reasons, no selective rerun-until-pass.

Fixtures include empty and malformed inputs, valid tiny/typical/limit files, non-ASCII UTF-8 byte boundaries, repeated-token/pathological candidate expansion, combined-byte/count overages, both C subpaths, V reproduced/mismatch cases, asset-load failures and cancellation during each real phase. At every stated byte limit, test L and L+1; at every count cap N and N+1.
