# WEB.6 prospective budget amendment — PROPOSED

2026-11-27. **Draft for owner decision and independent review; not adopted, frozen, implemented or tested.** Draft base: curated publication-source `329c0b8d8642ff3c07d258f9a7944c70f9dd1d14`. This draft changes no gate, count, criterion, runtime hold or implementation. WEB.3–WEB.6 remain planned; core remains 34/47 met, later gates 28/55 met plus two negative results. M3 execution/acquisition, hosted services and publication holds remain in force. Public-document reading and static local source inspection are the only research performed here.

## 1. Temporal prerequisite and proposed amendment

The [existing WEB.6 row](../../ROADMAP.md) requires further budgets to be frozen before WEB.1 starts. WEB.1 is already recorded met at implementation `51f29d7`. The owner-supplied research and [retained dependency audit](../reviews/web5-existing-claims-20261126/README.md) report no sufficient earlier freeze record located. The bounded record inspected here does not establish compliance with that temporal prerequisite. This proposal acknowledges it as missed on the available evidence; it does **not prove the absence of every possible earlier record**, invalidate engine results, or invent a retrospective freeze. A newly discovered earlier record would require separate provenance/scope review, not automatic historical compliance.

Propose replacing **only** this current WEB.6 sentence:

> Further budgets are frozen before WEB.1 starts.

with these exact sentences, subject to owner approval and independent review:

> The pre-WEB.1 budget-freeze prerequisite is acknowledged as missed on the available recorded evidence; this does not prove that no earlier record exists or establish retrospective compliance. Further budgets are instead frozen prospectively in a versioned, independently reviewed acceptance protocol before the WEB.6 conformance run; that protocol records the supported flows, byte and entry limits, device/browser versions, numerical thresholds, test counts, measurement limits and all baseline-dependent decisions. WEB.6 remains planned until its unchanged keyboard and input-boundary requirements and the prospectively frozen budgets pass with filed evidence and non-author review.

The other three criterion sentences remain **verbatim**:

> Accessibility and performance budgets are decided by counts. Each flow can be completed keyboard-only (k/k flows). A stated maximum input size applies, with a clear refusal above it, tested at the limit and one byte over.

This is a proposed text replacement, not an edit to ROADMAP. Adoption of an amendment would permit a later protocol freeze, not retroactively satisfy the original timing clause or itself close WEB.6. Existing WEB.0 start authorization is not requested again.

## 2. Scope and current constraints

The [source-validation ledger](web6-budget-source-validation.md) separates standards, guidance, engineering proposals and actual code observations. The recorded 1,128,365-byte WASM artifact is **uncompressed historical engine evidence** from `51f29d7`, not a current UI build, transfer budget, compilation measurement or browser support certificate. No new artifact was built or measured.

Static inspection of implementation `dcaa0d42e9de63d23aa113d9306134de9b28942c` finds a maximum configurable extraction input of **8,388,608 bytes (8 MiB)**. Shelf `86036c43394e94c1431ca335195a86e7754da6df` selects **1,048,576 bytes (1 MiB)** in its comparison extraction config. Neither is a verified browser-memory envelope. The wrapper reads a whole WASM response, copies complete input buffers into WASM memory and returns copied output; its exported processing calls are synchronous. Shelf comparison uses complete strings/catalogues; registration file pickers read whole buffers/text. These observations do not prove UI refusal before reading, bounded peak memory, cancellation, streaming or main-thread responsiveness. Effect-suppression flags are not computation cancellation. A worker-based design is a **practical proposed implementation constraint**, not a WASM/WCAG specification fact or existing parity result.

Required flow coverage must remain distinct:

| ID | Required operation and correctness basis | Proposed accounting |
| --- | --- | --- |
| F | WEB.3 Fingerprint: selected/dropped files to downloaded catalogue; exact CLI bytes, same pinned inputs/config | One of the original three flows; keyboard file-picker alternative required |
| C | WEB.3 Compare: catalogue–catalogue **and** catalogue–files; same report `bodySha256` as CLI | One flow, two mandatory subpaths; neither may be omitted |
| V | WEB.3 Verify: load report and required inputs, replay computation, display reproduced/non-reproduced digest | Third flow; registration-signature verification cannot substitute |
| D | WEB.4 sample/edit/transformation demonstration, including documented misses | Separate denominator: at least six fixed demos, at least half no-match/below-minimum, plus identity/unrelated self-checks |
| R | Shelf registration creation/signing and supplied-input registration verification | Separate two-task assessment; not evidence of V, complete WEB.3 or a hosted signer |

Proposed WEB.6 core keyboard count is **3/3 flows**, with **4/4 mandatory core subpaths** (F, both C subpaths, V); each must cover selection/input, config, start, cancellation when active, errors and result/export. D reports d/d separately; R reports 2/2 separately if that product is in the release. Missing core flows are **not tested/unimplemented**, never removed from k. Demo and registration results cannot inflate the core count. Future fixture matrices cross every implemented profile exposed by the candidate UI; deferred profiles stay explicitly deferred. Existing engine parity and historical copy reviews do not supply these UI counts.

## 3. Candidate limits and units

All values below are **proposed engineering targets for review**, not support promises. B means exact bytes; KiB = 1,024 B; MiB = 1,048,576 B. Network rates use decimal bits/s; ms and s are elapsed durations. Input text is counted as UTF-8 bytes, including encoded line endings, not JavaScript UTF-16 length or character count. No silent normalization, truncation or config increase is allowed. Limits are part of the displayed UI contract, distinct from smaller protocol/config limits.

| Limit | Candidate value | Proposed enforcement and boundary tests |
| --- | ---: | --- |
| Each source file or pasted source for F/C | `min(1,048,576 B, config.maxInputBytes)` | Preserve the selected config; preflight File.size or bounded UTF-8 encoding. Valid in-limit fixture at L, same fixture plus exactly one byte at L+1; assert clear refusal above L before engine processing |
| Source count and aggregate sources per job | 32 files; 8,388,608 B total | Check 32/33 and aggregate L/L+1, including individually valid files; sums checked without overflow |
| Each catalogue or replay-report document | 4,194,304 B | Both sides independently checked at L/L+1; bound raw read before parsing. Invalid/malformed documents tested separately from size rejection |
| Catalogue entry count | 1,000 entries per catalogue | Parse only after byte bound; test 1,000/1,001 valid entries; do not call this an engine limit |
| Combined input payload per core job | 8,388,608 B including report/catalogues/config/auxiliary bytes | One explicit byte ledger; count original bytes even when UI-to-worker framing expands them; also applies when individual limits pass; at L/L+1 tests |
| Exported catalogue/report | 8,388,608 B | Abort with explicit output-limit result; no downloadable partial or silently shortened output. Generation memory must remain bounded independently |
| Work concurrency | One active job per tab; at most one source loaded into engine at a time where catalogue API permits | Queue/reject second job clearly, never permit hidden multiplication of memory. Whole-job framing in the present API is a known design gap |
| R ancillary assessment only | Candidate 1,048,576 B artifact, 1,048,576 B each bundle/policy, 4,194,304 B aggregate request | New UI proposals, not current signature/registration limits; separate L/L+1 evidence, no key/storage/default-policy changes |

The source cap cannot be widened to 250 MB under this draft: the report supplies no browser capacity measurement, and 250 MB exceeds the engine's existing extraction config bound. The suggested 50 MB/20,000-entry catalogue and 500 MB memory promises likewise lack Traceweave evidence. They are not adopted. Even the smaller candidate limits above require baseline feasibility and independent boundary checks. For at-limit fixtures, distinguish successful size admission from any independently valid protocol refusal: record CLI-equivalent outcome, and include a well-formed fixture that actually completes each supported subpath. A timeout, crash or “too large” refusal at a promised in-limit case is not a pass.

## 4. Proposed numerical budgets and test methods

**E** = engineering target, not a standard; **B** = target requiring baseline/review before freeze; **S** = separately identified source criterion/guidance. Every E/B value is unmeasured here. A later freeze must fix or explicitly remove a proposed item with a reason; it cannot leave a blank while claiming complete budget compliance. No measurement permission is conferred by this table.

| ID | Proposed value and acceptance rule | Future measurement / rationale |
| --- | --- | --- |
| P1 E/B — shell transfer | Route-critical first-party JS encoded bodies sum ≤150,000 B; initial engine encoded body ≤1,200,000 B on first explicit use, shared engine counted once | Cold Network export, actual Content-Encoding and encoded/decoded body sizes, hashed asset manifest. Propose Brotli when negotiated and gzip fallback; test each negotiated encoding separately, without assuming either is already configured. Headers/protocol overhead reported separately. These numbers are candidate ceilings, not web.dev standards or compression predictions from historical bytes [L4–L6] |
| P2 E/B — loading | 5/5 cold runs LCP ≤2,500 ms and 5/5 warm runs ≤1,500 ms; separately shell controls ready ≤5,000 ms cold /1,500 ms warm | LCP is visible-content timing, **not interactivity**. Controls-ready mark requires handlers attached plus keyboard activation reaching an observable acknowledgement. Field p75 LCP guidance is a separate metric; five lab runs prove no field percentile [L1–L2] |
| P3 E/B — engine preparation | 5/5 first-use engine-ready ≤10,000 ms after explicit start including required fetch/compile; 0 attributable main-thread tasks >50 ms during preparation/processing | Record all tasks and trace compile/instantiate/copy/parse/render phases. Do not hide app-triggered GC as unrelated noise. 50 ms identifies long tasks, not an allowable total compilation duration. Streaming compilation can help but requires proper MIME/CSP and preserves import checks [L3,L6,L10] |
| P4 E — control response | 10/10 scripted interactions **per control, per core subpath, per required matrix cell**: Start from idle; Cancel/navigation during active work; next visible acknowledgement ≤200 ms | Event timestamp through painted feedback; manual keyboard counterpart. Report latency samples and worst value. This lab engineering target borrows a useful number from INP guidance; it is neither field p75 INP proof nor a numeric WCAG requirement [L1,L7] |
| P5 E/B — execution isolation | 0 bulk extraction/hash/parse/compare/replay calls on UI thread; dedicated worker proposed; 0 attributable processing tasks >50 ms on UI thread | Static call-path inspection plus trace; one shared engine may serve multiple flows. Transfer buffers rather than duplicate across worker boundary when possible, but account for WASM copies. An alternative design needs independent evidence meeting the same bounds before substitution [L3,L8–L10] |
| P6 E — honest status | Busy acknowledgement ≤200 ms; visible activity/status refreshed or confirmed at least every 1,000 ms during foreground work lasting >2,000 ms | Real phase/byte counters when available; otherwise indeterminate, explicitly no fabricated percentage or ETA. A UI heartbeat indicates responsiveness, **not engine progress**. Coalesce visible updates to at most 4/s; a stalled phase stays labelled honestly [L7,L11] |
| P7 E/B — bounded cancellation | 10/10 cancel probes at early/mid/late active phases per subpath/cell: acknowledgement ≤200 ms; stop accepting job results and terminate/finish computation ≤1,000 ms from cancel event | Deadline is unconditional in foreground tests: **no next-chunk exception**. Cooperative checks alone cannot interrupt a synchronous worker WASM call; host must be able to terminate worker by deadline, invalidate job ID, discard late messages and recreate safely. A job that has already finished is not a cancellation probe pass; baseline protocol must preselect workloads/phase triggers that permit active cancellation, then freeze them. No false success/download after cancel; new job starts within 2,000 ms. Termination is not memory-erasure proof [L9] |
| P8 E/B — completion | 5/5 repetitions for each fixed small/typical/limit/adversarial-valid job, per subpath/profile/cell: target ≤30,000 ms desktop and ≤60,000 ms real mobile | Fixed corpus/config/expected CLI outcomes pinned before timing; record exact duration and failure reason. These are feasibility targets needing baseline, not throughput promises. Explicit refused/ambiguous cases remain distinct from successful completion |
| P9 B — memory | Candidate WASM linear-memory high-water ≤134,217,728 B (128 MiB); accounted live input/output transfer buffers ≤33,554,432 B (32 MiB). Investigate whole-context incremental peak target ≤268,435,456 B (256 MiB) above idle | Observe linear memory growth and ownership ledger throughout worst expansion/repeated jobs. Buffer ledger excludes strings/DOM/parser/runtime overhead and cannot certify a total heap ceiling. Trace memory/OS process observations separately; sampling can miss peaks. Freeze whole-context ceiling only after a defensible instrument/matrix is chosen; no universal 500 MB claim [L12–L13] |
| P10 E/B — bounded IO | Source reads at most min(effective cap + 1, actual size) B; proposed read chunks ≤262,144 B; no unbounded whole-file read above declared limit | Static audit + future read-byte/allocation instrumentation for oversized/multibyte/aggregate cases. Current complete-buffer engine API may still buffer **within** the small cap; chunked File reads are not proof of streaming tokenization or O(1) engine memory. No arbitrary 25 MB exemption [L10] |
| P11 E — errors | 100% enumerated size/count/config/UTF-8/parse/network-asset/timeout/cancel/refusal cases have correct named item + text reason; 0 silent failures | Exact count n/n per scope; distinguish invalid signature/replay mismatch from IO error. Preserve input and recovery controls; focus stays predictable, error summary linked to field when useful, no routine forced focus into status [L7] |
| P12 E — keyboard and AT | 3/3 core flows and 4/4 core subpaths keyboard complete per required cell; 0 traps; 100% focusable controls visibly focused. Screen-reader status/error checks n/n on D1/D2 | Manual scripted picker/export/config/refusal/cancel/recovery flows; automated audits supplemental. Test light/dark, 200% zoom, narrow 320 CSS px layout, reduced motion; record resulting counts, not blanket WCAG certification [L7] |
| P13 E — announcement restraint | Polite start/phase/terminal messages; coarse real progress no more than once per 10 s;0 duplicate “still working” announcements when nothing changed | Accessible name and determinate value only when real; indeterminate has no false value. Progressbar alone is not a live region. Terminal state announced once promptly; record AT speech and actual DOM state rather than assuming role proves delivery. No 500 ms/1% speech stream [L7,L11] |
| P14 E — offline-after-load | 0 attempted network requests during each core flow **after explicit asset-ready point**, including errors/cancellation | Future browser traffic capture plus network denial after all required assets loaded; failed requests count as attempts. Lazy first-use loading occurs **before** asset-ready, not inside this window. Existing engine-only denial is not complete UI proof |
| P15 E/B — repeat load/caching | 5/5 same-document repeat operations cause0 engine body re-downloads after ready. If content-addressed static assets are used, propose max-age≥2,592,000 s with immutable; HTML revalidated | Verify real headers/asset versioning, not URL appearance. 30days is a proposed HTTP freshness policy, not guaranteed storage persistence. Current fixed `/wasm/tw_wasm.wasm` URL is not evidence of content addressing. Offline reload is a separate optional protocol requiring storage/privacy decision [L14–L15] |

No total processing duration is derived from Core Web Vitals. Field INP guidance is ≤200 ms at the 75th percentile of page visits, segmented by desktop/mobile; this draft authorizes no telemetry and promises no field assessment. Lab interaction traces, job duration, cancellation latency and memory are separate observations. Browser measurements and native engine parity must not be pooled.

Progress and cancellation expose actual design gaps: a worker stuck inside synchronous WASM cannot post genuine incremental progress or consume a cancel message until it returns. The proposed solution is honest indeterminate UI plus host-controlled termination; adding instrumented phases/chunking is future implementation, not a claim about current exports. UI timers cannot stand in for measured progress or prove that the worker is alive.

Memory API evidence is conditional. `measureUserAgentSpecificMemory()` is limited/experimental, requires a secure cross-origin-isolated context and returns implementation-dependent values. COOP `same-origin` and COEP `require-corp`/`credentialless`, permissions and resource compatibility require separate analysis; this draft does not authorize header changes that could break embedded resources/popups. Missing API support is “not measured,” never zero or pass. Prefer portable bounded-input/allocation evidence plus browser-specific traces; explicitly mark what remains unobservable before freezing P9 [L12–L13].

Measurement availability is a required per-cell record [L18]. Before future collection, feature-detect the observer itself and each needed `supportedEntryTypes` value in the relevant window/worker context; successful construction alone does not establish LCP, event timing or long-task coverage. Record unavailable entry types, empty/missed buffers, timer precision, trace tooling and instrumentation overhead. Empty observations are not evidence of zero long tasks or zero latency.

Fallbacks must retain the measured quantity: browser performance traces with input and presentation timestamps may substitute for event timing only when their precision and phase coverage support the same limit. A callback timestamp, UI heartbeat or `requestAnimationFrame` alone does not establish that feedback painted. If LCP cannot be observed, report LCP unmeasured; the separately defined shell-ready mark is useful diagnostics, not replacement LCP or INP. Where long-task observers are absent, an independently reviewed browser trace may provide equivalent main-thread duration/attribution evidence; a timer-lag check alone cannot prove the zero-long-task count. For memory, retain bounded-allocation and linear-memory evidence as separately scoped observations; neither a process sample nor a buffer ledger silently substitutes for an unavailable whole-context peak measurement.

A required metric/device cell without an adequate observer or reviewed equivalent is **unmeasured, not passed**. Report the denominator as planned/measured/passed, retaining unavailable cells. Before a conformance run, the protocol must resolve instrumentation or obtain an explicit reviewed change to the proposed metric/support envelope; it cannot claim the original threshold passed or silently drop the device after collection. This fallback policy authorizes no instrumentation deployment, header change or runtime test now.

Freeze exact model, CPU/RAM, OS/build, browser full version, AT version, power state, viewport, test harness and asset hashes before any future runs. Do not infer a browser version from “latest” after results. D1/D2 define the minimum proposed support candidates **only after** their frozen protocols pass. Hardware choice is an owner decision; neither model availability nor results are asserted. Registration R needs a distinct same-matrix result if shipped, with existing consent/key/storage boundaries unchanged. Background throttling, OS suspension, crash recovery and simultaneous jobs are outside these foreground latency promises and must be stated plainly, not used as exceptions during a foreground run. Feature detection can show a clear unsupported message; it cannot promise graceful recovery from arbitrary platform failures.

## 6. Reproducible prospective protocol and open decisions

Before a conformance run, independent review must accept a manifest with exact source/deployed-asset identity, fixtures/configs/CLI expected bytes, all limit dimensions, required cells, repeated-run order, measurement tools/versions and thresholds. A clean cold run clears HTTP cache and disables any existing service worker; warm means the same pinned assets loaded once, no source/user data persistence inferred. P2 means five cold navigations and five warm navigations to the same route/version; P3 first-use timing is recorded separately. Five cold/warm trials are small lab samples with all samples/max reported; do not relabel them as field p75. Keep profiled and unprofiled timings separate because instrumentation adds overhead. Predeclare invalid-run conditions (OS update/interruption/tool failure); preserve failed traces and reasons, no selective rerun-until-pass.

Fixtures include empty and malformed inputs, valid tiny/typical/limit files, non-ASCII UTF-8 byte boundaries, repeated-token/pathological candidate expansion, combined-byte/count overages, both C subpaths, V reproduced/mismatch cases, asset-load failures and cancellation during each real phase. At every stated byte limit, test L and L+1; at every count cap N and N+1. Record input SHA-256, actual byte count, expected admission/refusal, CLI outcome and observed outcome per case; label unsupported/deferred profiles explicitly. Correctness comparisons remain byte-exact/digest-exact as WEB.3 specifies; timings never excuse a wrong result.

Offline-after-load P14 does not imply an offline reload, first-ever offline visit or guaranteed cache persistence. A service worker/offline-reload policy would require a separate approved design, asset-only cache inventory, eviction/version-upgrade tests and reconciliation with WEB.2's no-storage-beyond-downloads wording. No service worker, local content cache, persistent input/key storage or changed WEB.2 interpretation is proposed for automatic adoption here. Shelf's explicit local storage/registration boundary remains separate.

Baseline-dependent before freeze: P1/P2/P3 actual startup assets and compile time; P5/P7 cancellable worker integration; every input/document/entry/output envelope in §3; P8 completion; P9 whole-context instrumentation/ceiling; P10 framing/read strategy; P15 hosting headers. These require future authorization, implementation readiness and measured baselines. Record proposed target, observed baseline, margin and accepted final value; any changed target needs justification/review before the conformance run, not after observing failures. No budget can be frozen by treating the historical WASM size as a new baseline measurement.

Owner decisions requested **for later disposition, not answered by this draft**:

1. Accept/revise the exact prospective timing amendment; acknowledge the missed prerequisite without retrospective compliance.
2. Choose the small candidate byte/entry envelope, minimum physical device/AT cells and budget targets for an independently reviewed baseline protocol. Do not adopt 250 MB/500 MB promises.
3. Decide whether worker/termination design and separate D/R scope are appropriate; preserve all three WEB.3 flows and original keyboard/boundary obligations.
4. Keep offline reload/persistent caching outside initial scope unless separately deciding its WEB.2/privacy implications. Decide how to measure memory honestly where APIs are unavailable.

Independent review and explicit later decisions are still required. This draft authorizes no runtime tests, builds, device purchases, downloads, services, M3 work, gate closure, public-history replay, push or deployment.
