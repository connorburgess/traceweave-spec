## 1. Question, and what the run does and does not show

**Question.** For two post-hoc image marks, TrustMark-Q and PixelSeal, does an **expected-payload test** behave as its analysis predicts on unmarked, wrong-key and wrong-entry inputs, and which edits, removal attempts and forgeries does it survive or accept, on one host, offline, on CPU?

This is the first study that tests the project's original goal directly: a recoverable mark embedded in content (UC-6, and UC-7 for images).

**What it shows if it passes:**
- The pinned code, weights and environment embed and recover a key-derived payload offline on CPU on this host, deterministically across two runs.
- On 100 synthetic images per scheme, clean marked images are accepted for their own entry at least 95 times in 100 (P1).
- The comparison and search code does not accept unmarked images, wrong keys or wrong entries (P2–P4: 0 accepts in 39,900 comparisons per scheme). **These are implementation checks.** With HMAC-derived payloads they are close to guaranteed by construction, whatever the images or schemes do (§6).
- Counts, with denominators, for 12 edits, 5 removal attempts and 3 forgery or overwrite attacks: residual transplant, **keyless re-embedding**, and overwrite.

**What it does not show:**
- **Anything about natural images.** Synthetic images are shapes, gradients, low-frequency texture and noise. They have no faces, text, fine natural texture or camera noise, and the learned marks were trained on natural photographs. A result here may be better or worse than on photographs, and no direction is predicted (§13, §16).
- **A false-accept rate.** 0 in 100 unmarked images bounds the per-source rate only below 2.95% (§13). The 10⁻⁶ figure is analytic and per comparison.
- **Authentication, ownership, ancestry or who embedded a mark.** A decoded payload is not signed. The decoders and encoders are public and unkeyed. **Anyone can copy a mark without the key**: decode a marked image's bits, then embed them into any other image with the same public encoder (condition `reembed`, §7). An accepted detection therefore shows only that bits matching the expected payload were embedded in the candidate. It does not show who embedded them, or that the candidate is, or derives from, the original.
- **Removal or forgery resistance.** Every removal and forgery count is a **lower bound on what an attacker can do**, never evidence of resistance. The protocol omits stronger attacks: learned forgers such as WmForger; VAE or diffusion regeneration; averaging or collusion over several marked images; optimisation against the public decoder; and adaptive combinations of the listed edits (lane 12, §16).
- **P2–P4 do not show** a false-accept rate, behaviour on natural images, or any resistance to forgery. There are two fixed public keys and 100 payloads per key, and decoder outputs cluster, so the 39,900 comparisons are a handful of realizations, not 39,900 independent trials.
- **Equality across hosts.** One macOS arm64 host; cross-host is not tested.

## 4. Schemes, payloads and keys

**Keys.** Two study keys: K_A = SHA-256("traceweave e-img-m-1 study key A (public test key)") and K_B likewise with "B" (`twmark/payload.py`). The key strings keep the label `e-img-m-1`, so the keys and payloads are unchanged in `e-img-m-2`. They are **public test values**. The study tests the statistic, not key secrecy. A deployment would draw a secret random key per creator (UC-7).

**Payload.** For key K, scheme s and entry id e, the bits are the first n bits, most significant first, of HMAC-SHA256(K, "e-img-m-1|s|e"). The string `e-img-m-1` in that rule is the payload-derivation id. It is kept unchanged in `e-img-m-2`: the rule is the same, and only the protocol version changed.

**Identity binding.** The payload is a keyed function of the catalogue entry id. A verifier holding the key recomputes the expected bits for each entry and tests agreement (§5). Nothing else binds identity: there is no signature over the payload, no binding to the image's content, and no version or framing field of ours.

| Scheme | What is embedded | Tested bits n | Settings |
| --- | --- | --- | --- |
| `tm` TrustMark-Q | 61 data bits = the payload with n = 61, BCH_5-encoded by upstream `DataLayer` into 100 transmitted bits: data at positions 0–60, 35 ECC bits at 61–95, 4 version bits `0001` at 96–99. The adapter checks the length before calling the encoder, because upstream `process_encode` silently truncates or pads (lane 08) | **61: raw positions 0–60 only** | `use_ECC=True`, `encoding_type=BCH_5`, `WM_STRENGTH=1.0`, `WM_MERGE='bilinear'`, `concentrate_wm_region=1.0`, `device='cpu'`, upstream `encode(…, MODE='binary')` |
| `ps` PixelSeal | the 256-bit payload | 256 | model card as pinned (`scaling_w` 0.2, JND attenuation `jnd_1_1`, `img_size_proc` 256); `embed(…, is_video=False)` with upstream default interpolation; output `round(clamp(x, 0, 1) × 255)` half to even |
| `dw` `dwtDct` (control) | the 32-bit payload, via `set_watermark('bits', …)` | 32 | library defaults (`scales=[0,36,36]`, `block=4`); RGB↔BGR swapped at the boundary |

**Raw bits** (`raw_bits`), before any error correction:
- `tm`: upstream `decode()` up to the sign of the decoder output. That is `get_the_image_for_processing`, a BILINEAR resize to 245×245, the decoder network, then `> 0`. There is no detector, rotation search or BCH. A unit test checks that BCH-decoding these bits equals upstream `decode(MODE='binary')`.
- `ps`: upstream `detect(…, is_video=False)`, then `preds[0, 1:] > 0`, averaged over space first if the output is spatial.
- `dw`: upstream `WatermarkDecoder('bits', 32).decode(…, 'dwtDct')`.

**Which bits are tested, and why they can be treated as independent.** The analysis in §5 needs every tested expected bit to be a fair coin, independent of the other tested bits and of the candidate, when the key is random. That holds exactly for bits that are **direct HMAC output**. It fails for bits computed from other bits or fixed by the format (review B1):
- `tm`: only the **61 data positions**. They are the HMAC output itself. The 35 ECC bits are a linear function of the data bits, and the 4 version bits are `0001` for every payload. A marked image of a different entry, or any decoder that has learned the format, agrees on those 39 bits more often than chance. Agreement on all 100 transmitted bits is still recorded, as `agree100True`, but it is report-only.
- `ps`: the **256 payload bits**, `preds[0, 1:]`. They are the HMAC output; PixelSeal adds no ECC. The detection channel `preds[0, 0]` is not tested.
- `dw`: the **32 embedded bits**, which are the HMAC output; there is no ECC.

The bits are independent **over the key**, not over images: a decoder may emit structured or repeated strings, which §5 handles.

**TrustMark's blind BCH result** (`bch.valid`, `bch.dataEqualsTrue`) is recorded for every TrustMark query. It **never** enters the decision (lane 10 "After the report audit": a BCH-valid decode is not presence evidence).

**Keyless re-embedding.** `forge_bits` is what an attacker with only the public code and weights would re-embed after decoding a marked image. For `tm` it is the BCH-corrected 61 data bits when BCH succeeds with version 1, and otherwise the raw positions 0–60; which one was used is recorded in `forgedFrom`. For `ps` and `dw` it is the raw bits. `embed_bits` embeds them with the same public encoder. No key is used.

**Marked artifact.** The marked array is encoded as PNG (`compress_level` 6), then decoded again. That PNG is the published artifact; every condition starts from its decoded pixels.

**No download at run time.** Upstream TrustMark fetches missing model files; the adapter replaces that method with one that refuses. PixelSeal is built with upstream `setup_model` from the local checkpoint, never `videoseal.load`. Every model file's size and SHA-256 are checked before it is loaded.

**Import-only dependencies.** `av` and `pycocotools` are replaced by fail-on-use stub modules before videoseal is imported (lane 12). Any attribute use raises `StubUsed`, which would abort the run.

## 5. Decision rule and false-accept analysis

**Statistic.** For raw bits r and expected bits e of the same length n: the agreement m = #{i : rᵢ = eᵢ}.

**Threshold.** Accept iff m ≥ k(n), where k(n) is the smallest k with P(Bin(n, ½) ≥ k) ≤ 10⁻⁶, computed exactly with integers (`payload.k_for`). Frozen values:

| Scheme | n | k | P(Bin(n, ½) ≥ k) | at k − 1 |
| --- | --- | --- | --- | --- |
| `tm` (61 data bits) | 61 | 49 | 9.85 × 10⁻⁷ (exactly 2,271,115,189,673 / 2⁶¹) | 3.83 × 10⁻⁶ |
| `ps` | 256 | 167 | 6.22 × 10⁻⁷ | 1.18 × 10⁻⁶ |
| `dw` | 32 | 30 | 1.23 × 10⁻⁷ | 1.28 × 10⁻⁶ |

For PixelSeal the rule gives X1's k (167/256; [audit](../lanes/10-report-audit.md)). For TrustMark it does not: X1 tested 74 of 100 transmitted bits, and the `e-img-m-1` version of this protocol copied that. Review B1 showed that test's per-comparison tail is not 10⁻⁶. With the 4 fixed version bits always agreeing, it effectively needs 70 of the other 96 bits, which gives 4.02 × 10⁻⁶. And ECC structure makes wrong-entry agreement follow the code's weight distribution, not a binomial. The 10⁻⁶ target is the audit's per-key figure.

**Search.** Each query is tested against all N = 100 entries of one key (key A, except where §7 says key B). The query outcome is:
- `match` if exactly one entry is accepted;
- `ambiguous` if two or more are;
- `no-match` if none is;
- `abstain-<code>` if the bytes cannot be decoded (`undecodable`), are not 8-bit RGB (`unsupported-mode`), or are below a scheme's minimum size (`too-small`; `dwtDct` refuses under 256×256 pixels).

A positive is **correct** when the outcome is `match` and the entry is its own.

**False-accept analysis.**
- **One key, one expected payload, any input.** The payload is an HMAC output that the input image and the decoder never see. So for any fixed raw string r, including the structured outputs X1 saw from unmarked images, the agreement with a payload under a uniformly random key is exactly Bin(n, ½). P(accept) = P(Bin(n, ½) ≥ k) ≤ 10⁻⁶ per comparison. The probability is over the key, not over images, and it assumes HMAC-SHA256 behaves as a random function.
- **N catalogue entries under one key.** Per query, P(any accept) ≤ N × 10⁻⁶ by the union bound: ≤ 10⁻⁴ for N = 100.
- **N_K keys** (several creators, or key rotation): ≤ N_K × N × 10⁻⁶ per query.
- **Many queries under one fixed key are not independent trials.** If the decoder returns nearly the same string for many unmarked images, and that string happens to agree with some entry's payload at ≥ k bits, all of those images are accepted together. The analytic bound still holds for each comparison and by the union bound over all of them: with C comparisons, P(any accept) ≤ C × 10⁻⁶. But the observed count is clustered. This is why the record keeps the number of distinct raw strings among unmarked images and the maximum agreement with any entry (`agreeMaxOtherHistogram`). The observed per-source bound is reported separately (§13), as the audit requires.
- **Per scheme**, using the bound above: P4 (9,900 wrong-entry comparisons) ≤ 0.0098 for `tm` and ≤ 0.0062 for `ps`; all of P2–P4 (39,900 comparisons) ≤ 0.039 for `tm` and ≤ 0.025 for `ps`.
- **What the analysis does not cover.** A marked image's decoded bits are not independent of its own payload, so the bound says nothing about overwrite, transplant or forgery, where an attacker copies or re-embeds a real mark. Those are measured counts (§7) with no bound. Nor does it cover a decoder bias that coincides with how payloads are derived, which HMAC rules out unless HMAC is broken.

If W1, W2, W4, W5 or W6 fails, the run is a **negative result for the harness**, and no pass line is read.

**W3 rule** (review M2). Neural decoders on CPU are deterministic on one host only while the thread count, the libraries and the operating system stay the same. A change in any of them alters the order of float reductions. `compare` therefore classifies a difference:
- **exit 5, invalid:** the outputs differ, but every recorded input is equal. The recorded inputs are environment, runtime pins and versions, weight digests, sources, goldens, protocol digest and HEAD. The pair is **invalid, not a result and not negative**. It is rerun as a fresh pair on the pinned host, under the same version, after checking that no other process changed the machine's state. At most two such reruns are made. If a third pair is still invalid, the owner decides, and any change is a new version.
- **exit 1, negative:** the outputs differ and some recorded input differs between the two runs. The harness failed to hold its inputs fixed, so W3 is a negative result for the harness.

Every invalid pair is kept and reported, with its `compare` output.

**Pass lines.** These apply to the two candidates only. Each was justified before any experiment-range data existed.

| ID | Pass line, per candidate scheme | Justification before data |
| --- | --- | --- |
| P1 | clean marked images correctly matched ≥ **95 of 100** | Both authors report near-perfect clean recovery on natural images (lane 08 I; X3). A threshold at about 80% (49/61) or 65% (167/256) bit agreement leaves wide margin. This is a premise check: a scheme that cannot recover its own clean mark on these images is not tested further by this protocol. The 5-image allowance covers decode failures that synthetic content might cause. It is not derived from data |
| P2 | **implementation check:** unmarked inputs accepted for any entry, **0** in 20,000 comparisons (100 covers + 100 hosts, × 100 entries) | Union bound over 20,000 comparisons ≤ 0.02 (§5). An accept would most likely mean a bug, such as payload reuse, a wrong comparison or the wrong bits tested |
| P3 | **implementation check:** clean marked images accepted under the wrong key (key B, all 100 entries), **0** in 10,000 comparisons | Same analysis: ≤ 0.01 |
| P4 | **implementation check:** clean marked images accepted for a wrong entry under key A, **0** in 9,900 comparisons | Same analysis: ≤ 0.0099. Payloads of different entries are independent HMAC outputs |

**What P2–P4 are** (review B2). With HMAC payloads, an accept needs a decoded string to hit a pseudorandom 61-, 256- or 32-bit target. So zero accepts is expected whatever the images or the schemes do. These lines check that the payloads, comparison and search are implemented correctly: no payload reuse, the right bits compared, the right key searched. They are **close to guaranteed by construction**. They do **not** measure a false-accept rate, say anything about natural images, or show resistance to forgery: a forger copies a real mark (`reembed`, `transplant`) instead of guessing one. There are two fixed public keys and clustered decoder outputs, so the 39,900 comparisons are far fewer independent chances than the number suggests. Every report of P2–P4 MUST carry this paragraph, or point to it.

The verdict per candidate is **met** if W1–W6 hold and P1–P4 all pass. If W1–W6 hold and any P fails, it is **negative-result**, and the failing line is reported. For P1, a negative result means "fails on this synthetic set", nothing more. Neither verdict says anything about natural images.

**Report-only, no pass line.** All other counts: the 12 edits, the 5 removal attempts, transplant, overwrite, TrustMark blind-BCH validity, the quality figures and the negative control. There is no basis before data for a survival rate on synthetic images, and inventing one would repeat the error the lane 10 audit flagged (invented gates).

**Stated expectations, not pass lines** (written down so that the result can be compared with them):
- E1: transplant is accepted for most TrustMark and PixelSeal entries. The residual is added, not bound to content (lane 10 finding 5; F7 reports 80–91% for TrustMark-P against learned forgers).
- E2: ReMark removes most TrustMark marks (lane 08: 55% bit accuracy at 48.5 dB).
- E3: `dwtDct` fails the expected-payload test on many conditions where the candidates pass. That is its purpose as a control.
- E5: keyless re-embedding (`reembed`) is accepted for M's entry about as often as P1 for both candidates. It is a clean marking of H with M's bits, so a detection cannot distinguish the original from a copy.
- E4: overwrite with key B makes the key-B payload accepted and the original key-A payload rejected for most TrustMark entries (TrustMark FAQ: TrustMark does not co-exist with itself).

**PSNR floor.** 38.0 dB between the cover and the marked image, over all RGB samples. The floor is 4 dB under the lowest author or X1 mean for the candidates (TrustMark-Q about 42–43 dB). It marks a marked image that UC-7 would refuse to publish. It is a policy line, not a calibrated perceptual threshold. Marked images below it are counted (`quality.belowFloor`) and **still tested**, so every denominator stays 100. The report lists how many successes come from images below the floor.

Tested for M's own entry. No key is used | A | forgery |
| 21 | `overwrite` (original) | M re-marked by the same scheme with key B's payload for the same entry id, as PNG. Tests whether the original key-A mark survives | A | overwrite-original |

`overwrite` original and new share one set of bytes, and `wrongkey` reuses the `clean` decode. Each entry therefore has 25 query lines, counting `cover` and `host` once per entry. **Per scheme: 2,500 query lines** = 100 × 23 conditions (1–23) + 100 covers + 100 hosts. **Across the three schemes: 7,500.** If the clean decode abstains, `reembed` and `wrongkey` are skipped for that entry and the denominator shrinks; this cannot happen for 8-bit RGB PNGs of the stated sizes.

**Forgery and transplant, what counts.** For `transplant` and `reembed`, `acceptedAsTrue` counts forged images accepted as the donor's entry: the attacker's success. `reembed` is the stronger forgery. It needs only the public decoder and encoder, and it produces a clean mark on H, whereas `transplant` adds M's residual, which was shaped for C. For `overwrite` it is reported both ways. The wrong-key condition reuses the clean decode, so it needs no extra decode.

## 8. Offline execution, environment and inputs

- **Online steps, once, before the work tree is frozen:** `fetch_wheels.py` (PyPI, 49 files by SHA-256), `fetch_sources.py` (GitHub archives; 84 files by SHA-256 and git blob id), `fetch_weights.py --pin` (the two weight hosts; 6 files by size, publisher digest and SHA-256). ## 9. Execution order and code identity

1. **Clean tree at the frozen commit.** `git worktree add <dir> <frozen-commit>`. The shared checkout carries other lanes' uncommitted work and cannot pass the clean-tree check.

   - **(i)** logs and checks its code identity (`codeIdentity`):

**Abort rule.**
- A run whose elapsed time exceeds **4 h**, about 3 times the estimate, stops at the next query. It writes only `summary.json` with status `aborted-time-limit` and no counts, and exits with status 3.
- An aborted run is not a result. It may be repeated under the same version on a less loaded machine.
- If two consecutive runs abort, the owner decides what to do, and any change is a new version.
- A run that fails for memory is reported as failed.

## 13. Statistical limits

All bounds are exact one-sided 95% Clopper–Pearson bounds and assume independent trials. The trials are not independent (§5): edits of one image are correlated, all images come from one generator, and every comparison under one key shares that key.

| Observation | What it bounds at most |
| --- | --- |
| 0 of 100 covers or 0 of 100 hosts accepted | per-source rate below 2.95% for that set, for this generator and these 100 payloads |
| 0 of 200 unmarked accepted (covers and hosts together) | below 1.49% per source |
| k of 100 for one condition | a 95% interval about ±4 to ±10 percentage points wide, depending on k |
| 0 accepts in C comparisons | consistent with the analytic ≤ C × 10⁻⁶. It does not measure it: that would need on the order of 10⁶ independent sources |

## 15. Changes that need a new protocol version

Any change to:
- the seed plan, image counts or generator;
- a scheme, a model file, the upstream sources, or scheme settings;
- the payload rule, keys, n or k;
- a condition's definition or encoder settings;
- W1–W6, P1–P4 or the PSNR floor;
- the record field sets;
- package versions or hashes, Python minor version, platform, or any runtime pin of §10 (thread counts, thread variables, deterministic algorithms, OpenCV threading);
- the tested bit positions, or the W3 rule;
