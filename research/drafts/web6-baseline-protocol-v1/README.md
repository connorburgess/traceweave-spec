## 3. Fixture recipes, byte envelopes and correctness

Candidate limits remain those of the reviewed proposal, encoded in `candidateTargets`: each source is min(1,048,576 B, selected config.maxInputBytes), 32 sources and 8,388,608 B source aggregate; each catalogue/report 4,194,304 B; 1,000 catalogue entries; total core input 8,388,608 B; export 8,388,608 B; one active job/tab. R remains separate: artifact/bundle/policy 1,048,576 B each and request 4,194,304 B total. These are distinct lower UI/request envelopes, not a widening of the current 8,388,608 B hard engine extraction bound or a promise of browser capacity.

B is exact bytes; KiB=1,024 B; MiB=1,048,576 B. Count UTF-8 source bytes and actual serialized config/document/auxiliary bytes, including path/identifier bytes supplied as auxiliary inputs, exactly once in an explicit input ledger. Pasted UTF-16 string length is not the byte measure. Track framing/copies/strings separately for memory; do not hide them by counting only payload bytes. No silent truncation, config increase or normalization.

**Interacting limits are explicit.** The equal 8 MiB source-aggregate and combined-input candidates mean a source aggregate at 8 MiB plus mandatory config already exceeds the whole-job limit. `source-aggregate-L` is therefore a limit-predicate admission check paired with an expected combined refusal, not a successful full-flow fixture. At integrated combined L, the feasible source allowance is `8,388,608 - actual(config + documents + auxiliary bytes)`. Freeze those actual bytes before generating fixtures; check that the remainder is nonnegative. Two 4 MiB catalogues plus config similarly exceed the combined cap. Test per-document limits with a small opposite catalogue; never report an impossible all-limits-saturated job as a completing boundary pass. Independent preparation review must confirm each fixture's dimension/expected precedence and any dominated limit.

The ledger includes tiny/typical/limit/adversarial-valid slots per F/C/V subpath, source/UTF-8/empty/malformed boundaries, 32/33 files, source and combined L/L+1, left/right catalogue and replay-report L/L+1, 1,000/1,001 entries, output L/L+1, concurrent-job refusal, V reproduced/mismatch and asset failure. Slots are recipes, not generated data or observed expected output. Expand parameterized malformed/config/UTF-8/error variants into distinct fixture IDs before freeze; do not call a family one exhaustive test. Each completing in-limit fixture needs a valid grammar/config and CLI-bound outcome; size admission alone is not successful completion. Protocol refusals/ambiguity and UI size/timeout errors remain distinct. Expose any impossible output-boundary fixture or unavailable instrument before running, rather than fabricate output lengths.

F downloads exact CLI catalogue bytes. C catalogue–catalogue and catalogue–files each reproduce `bodySha256`. V replays report computation with required inputs, including a mismatch case; registration-signature verification cannot substitute. Every exposed implemented profile gets at least one explicit profile/config tuple per applicable core subpath; enumerate mixed/config variants and boundary obligations before freeze. Deferred profiles remain named exclusions. Exact profile tuple IDs and expected CLI hashes are currently null.

## 5. Unique core cancellation denominator and validity

`coreCancellationBuckets` explicitly lists 24 **minimum template buckets**: four subpaths × two physical cells × three phases, each planned 10, measured 0, passed 0. `profileTupleId=null` means these are unresolved minimum slots, not a frozen one-profile implementation claim. Ten per bucket yields 30 per subpath/tuple/device, 120 per device, **240 minimum**. With `p_s` exposed profile/config tuples for each of four subpaths, expand to **60 × Σ p_s**; uniform p gives 240p. D3 diagnostics are separately 30 × Σ p_s (minimum 120), never pooled with D1/D2. Freeze every expanded bucket ID/count before collection.

Early means real input read/decode after admitted work starts; mid means real bulk engine work; late means actual output-copy/serialization/finalization before result publication. A finished job waiting for a download click is inactive. Bind each tuple's workload, phase-entry/exit activity evidence, cancel trigger and calibrated/common timeline. Artificial idle barriers cannot be the sole activity evidence. If bounded workloads are too fast or a phase is absent/unobservable, retain the unavailable planned bucket and resolve feasibility or a reviewed pre-run revision; no post-run denominator reduction.

Each of ten slots needs an active event before phase exit/job completion/publication, adequate clock/observer evidence, acknowledgement/cessation/restart measurements and no late-result publication. Completed-before-cancel attempts are invalid/inactive, not successes; record them and leave the slot unmeasured until a replacement allowed by frozen validity rules is collected. Preserve valid deadline failures; never replace them with repeats until ten successes mask the failure. Report planned/valid-measured/passed, every invalid attempt and unavailable slot per bucket. P4 observations can be cross-referenced only when they satisfy all P7 validity conditions; no double count. No runtime feasibility is asserted.

## 6. R commit-aware cases and separate D scope

R is conditional on candidate release scope; `shippedInCandidate=null` is unresolved, not “out of scope” by default. Preserve the reviewed six states R0/RK/RS0/RS1/RB/RC. Cancel stops scheduling future steps; it cannot undo persisted keys, completed signing or stored cards. P7's 1 s disposable termination/result-discard promise does not govern those commits. Before each not-yet-entered commit, cancellation guard ordering must be observable; an already-entered sign/store settles truthfully. A queued click received after a synchronous write cannot be backdated.

The ledger has 19 separate R scenario families, proposed three repetitions per required physical cell: 16 creation/error/recovery scenarios(96 planned) plus three standalone verification scenarios(18 planned), **114 conditional planned observations**, outside core 240. Freeze expansion for every actual reused/new-key/error/late-action variant before R execution; family coverage is not an exhaustive claim. R keyboard tasks are separately 2/2 per physical cell (4 minimum), never proof of core V or cancellation. These candidate allocations are prepared here, not adopted/frozen.

Future R execution must use an explicitly scoped isolated test browser/storage profile and synthetic operator-controlled inputs/keys under existing consent controls, not a real user keystore; this preparation is not consent to create keys. No implicit rollback/deletion becomes permitted as test cleanup. Observe key reused/new and write started/confirmed/failed/unknown; sign started/completed/error/unknown and signed-bundle digest; verification complete/not complete/error; card ID and attempted/acknowledged/reconciled/failed/unknown store status; operation/request digest, stop acceptance boundary/time and terminal/partial/pending outcome. Retain an existing signed bundle in transient recovery context rather than discard it as a late disposable result. Session-visible readback is not durable flush. Reload receipt loss or concurrently changed storage stays explicit unresolved outcome.

R candidate acknowledgement≤200ms; within 1,000 ms report reconciled result or truthful pending, **not** a promise that sign/store stopped. Separate settlement target 30 s desktop/60 s mobile: exceeding it fails the target while preserving pending/unknown state; late completion updates the same receipt without resumed skipped steps. Post-store success remains completed/saved with stop too late, not cancelled with no effects. Errors preserve known partial effects. Recovery reads existing records only: no implicit deletion/rollback/new key/re-sign/save retry/trust change, persistent receipt journal or external action. Any deliberate new action uses existing consent and a new operation ID. No new consent/storage authority is granted.

D is a separate optional-in-release assessment: six planned demo recipes, at least three no-match/below-minimum, plus distinct identity and unrelated self-checks. Recipes include reformat, rename, reorder and evasion/fragment/unrelated cases; no output class is a measured result. Pin intended negative recipes to actual CLI outcomes before freeze or revise them with review; do not relabel observed positives to meet the half-negative requirement. D reports d/d and R 2/2 separately; they do not dilute core 3/3 or 4/4.
