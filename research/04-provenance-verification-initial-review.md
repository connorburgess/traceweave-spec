# Private provenance: initial review

Reviewed 2026-11-18. Original preserved unchanged in ignored local input perplexity/04-provenance-verification.md. Google report pending. This is a targeted protocol review, not a cryptographic audit or adopted schema.

## Assessment

Useful direction: exact signed bytes, separate verification outcomes, offline-first operation and optional timestamps. The proposed Go/Rust interoperability harness is a sensible candidate after library selection. The report cites external specifications, unlike the detection report, but did not inspect core.md and therefore misses existing commitment details. It supplies no pinned Rust DSSE/TSA library or concrete compatibility matrix; implementation readiness remains unestablished.

## Corrections and missing decisions

1. **Use the existing commitment before proposing a replacement.** [Core](../spec/core.md) already specifies SHA256(D || R || L || C), a fixed domain label, 32-byte private random nonce, unsigned 64-bit big-endian catalogue length and exact catalogue bytes. Opening discloses the entire catalogue and nonce. The report's references to selected entries/minimal openings suggest unsupported selective disclosure. Treat such a design as a separate future protocol, not a property of the current hash. Retain exact configuration/catalogue bytes; normalization and canonicalization are not implicit.
2. **Distinguish structural checks from cryptographic opening.** The hash can commit to arbitrary bytes, including a structurally invalid catalogue. Opening consistency and catalogue schema validity are separate outcomes. A correct opening demonstrates consistency under the commitment assumptions, not creation, ownership or possession at a historical time. Timestamped commitments can support prior existence when later opened under explicit hash/preimage assumptions; avoid categorical claims that discard that conditional evidence.
3. **The signed-byte boundary is correct.** [DSSE v1.0.2](https://github.com/dsse-lf/dsse/blob/v1.0.2/protocol.md) signs PAE over payload type and decoded payload bytes. JSON reserialization is not part of verification. Deterministic payload generation may help reproducible fixtures, but arbitrary valid producers need not independently emit identical JSON bytes. Test cross-verification of the same payload separately from any project-specific serialization convention. Unsigned key identifiers must not establish trust on their own.
4. **Fix tampering test meanings.** Editing the subject/configuration inside an existing signed payload invalidates its signature. Presenting a different candidate artifact against an intact signed record can yield signature-valid plus subject-mismatch. A newly signed false subject claim is a third case. Define these separately instead of assigning subject-mismatch to every changed-subject test. Legitimate outer-envelope reserialization need not fail merely because unsigned bytes changed; reject malformed/ambiguous fields and enforce declared envelope policy.
5. **Timestamp the intended object.** [RFC 3161](https://www.rfc-editor.org/rfc/rfc3161) binds a message imprint. Timestamping a payload alone does not establish when a later signature over it existed. Define whether the timestamp covers payload, signature, commitment or a framed evidence object. Validate the imprint, token signature, TSA certificate purpose/chain/policy, nonce if requested, time/accuracy and relevant revocation evidence. Include [RFC 5816](https://www.rfc-editor.org/rfc/rfc5816), which updates certificate identification, and an errata review. These were not completed in the report.
6. **Separate mathematical validity from policy acceptance.** Expiry or revocation need not change the signature equation's result. Historical trust depends on time evidence and verifier policy. Missing optional time evidence is not an invalid local signature; an overall acceptance policy may nevertheless require time. Do not equate current certificate expiry with automatic invalidity of every historical timestamp.
7. **A bundle is not a trust root.** [Sigstore bundle documentation](https://docs.sigstore.dev/about/bundle/) describes packaged verification material. Verification still needs expected identity, trust roots and policy; optional log/timestamp modes need version-specific testing. Offline artifact verification and online creation/issuance are different properties. A TSA interaction can disclose timing, client/network identity and account context in addition to the imprint.
8. **Finish artifact binding and library selection.** State which artifact is the outer in-toto subject, how original/final/observed candidate digests relate, and how mark IDs are assigned before embedding without circular dependencies. Identify exact Go/Rust signing and verification libraries, supported algorithms/formats, licenses and maintained versions. Do not add ownership/legal-verdict fields merely because the report proposes them.

## Smallest next verification increment

Select an existing DSSE implementation pair and a supported signature algorithm; use public test-only keys and existing exact-byte vectors. Cross-verify fixed payloads, then test payload/type/signature mutations, unsigned envelope variations, untrusted keys, candidate mismatch, duplicate-key payloads, input limits and the existing full commitment opening. Preserve separate verdicts and never execute candidate code or automatically fetch references. Optional timestamps follow as a separate integration with a clearly specified target digest. No new cryptographic primitive, selective disclosure or production key material is required for the first harness.

No signing implementation or interoperability experiment was executed for this review. The proposal remains pending the Google comparison and concrete library evidence.
